# WP-05B3C2: Durable Crawl-Attempt Claim Design

## Status

**Stage B hardened; production activation is NOT approved.**

The maintainer approved the additive schema-1.17 attempt objects, the
`legacy`/`fenced` cutover in `update_sources`, and the internal opt-in claim API
for disposable tests only. WP-05B3C2C adds the exact history reference,
concurrency-safe mode locking, fail-closed attribution and generation recovery
described below. Schema remains 1.17 and writer generation remains
`verified-ownership-v1.17`.

Implemented in this package:

- PostgreSQL and SQLite fresh-install and v1.16 -> v1.17 attempt objects;
- repeatable same-version development addons with fail-closed guards;
- the `source-crawl-attempt-v1` capability marker and read-only readiness check;
- the atomic claim repository in `pkg/database/source_crawl_attempt.go`;
- fenced `update_sources` behavior for PostgreSQL;
- an exact current-claim reference to one history row;
- a shared-advisory-lock mode protocol with an operator-only mode function;
- fail-closed attribution when any competing operation is malformed;
- high-water generation recovery when the current claim row is absent;
- SQLite and disposable PostgreSQL integration tests.

No crawler, worker, event consumer, agent, MCP client or production service
constructs or calls the claim API. No terminal result is recorded.

## 1. Verified baseline facts

- `cmd/thecrowler/main.go:retrieveAvailableSources` opens one bounded
  transaction and calls `update_sources($1..$7)`.
- PostgreSQL `update_sources(...)` at
  `pkg/database/postgresql-setup.pgsql:3116` locks eligible `Sources` rows with
  `FOR UPDATE SKIP LOCKED`, sets `status='processing'` and `engine`, and returns
  source columns only.
- SQLite has no `update_sources` function; ordinary SQLite crawling therefore
  uses no SQL source-claim path. MySQL has an independent procedure that returns
  only source columns.
- `CrawlProposals` stores `request_id`, `run_id`, `agent_id`, `owner`,
  `principal_user_id`, `source_id`, `operation_type`, `proposal_sha256`,
  `state`, expiry and submitted `operation_id`.
- `CrawlApprovals` stores the approval/proposal/run/agent/owner/principal/source
  binding, approval hash, approved-at, expiry and revocation.
- `Status` stores a crawl operation keyed by `status_sha256 = operationID`, with
  `agent_id`, `source_id`, `operation_type`, `status` and strict `details`.
- `pkg/crawler/types.go:Pars` and `Status`, and `pkg/crawler/process.go:
  ProcessContext`, carry `cdb.Source` and metrics only. Neither carries an
  operation ID, attempt ID or fence.
- `pkg/crawler/crawler.go:closeSession` updates `Sources.status` through
  `UpdateSourceState` and optionally emits a source-level `crawl_completed`
  event. It does not address an operation row.
- No existing table or column connects a durable `operationID` to one crawler
  attempt.

## 2. Claim protocol

The proposal is a new internal opt-in path; the current legacy path remains in
place until an explicit fenced-mode cutover. The current claim can refer to only
one exact history row: the composite `(source_id, generation, attempt_id)`
foreign key prevents a mix of one attempt's ID with another attempt's generation.

1. Begin one bounded transaction.
2. Read the singleton `SourceCrawlClaimPolicy`. If its mode is `legacy`, return
   `legacy_mode` without mutation. If the attempt schema/marker is absent, return
   `unsupported`/`unavailable` before mutation.
3. Require a trusted 64-hex `ClaimRequestID` generated by the engine (never a
   model, event or web value). If any attempt already exists for this claim
   request, return those stored attempts without allocating new generations.
4. Take the shared advisory policy lock, then select eligible sources with the
   same priority, status, disabled and stale processing rules as
   `update_sources`, ordered by `sub_priority DESC, source_id ASC`, with
   `FOR UPDATE OF s SKIP LOCKED` on PostgreSQL. A source with an unexpired
   current claim is excluded; an expired claim permits a new generation. SQLite
   serializes writers at database level.
5. For each locked source:
   1. Recheck the source is live and enabled.
   2. Recheck current verified source ownership against
      `Sources.usr_id` + `SourceOwnership`.
   3. Compute the next generation and a newly generated 64-hex attempt ID.
   4. Mark the previous attempt row `superseded`, with the new generation and
      terminal time, **before** inserting the new attempt. This frees the
      active-operation partial unique index for a legitimate rebind.
   5. Upsert the current claim row with the new attempt ID and generation.
   6. Insert the immutable attempt-history row as `claimed`.
   7. Update `Sources.status='processing'` and `Sources.engine`, preserving the
      existing source result shape.
6. Read candidate operations for the source without locking proposal rows. The
   source row is already locked, so a concurrent submission either committed
   before the lock (visible) or is waiting on the source (not visible).
7. Validate the candidate set and, if exactly one trustworthy candidate exists,
   write its immutable operation binding to the just-created attempt row **before
   commit**. No committed attempt binding is ever updated.
8. Commit the source claim, current claim, history and optional binding
   atomically.
9. Return the attempt ID, generation, source IDs and a closed attribution result.

`update_sources` keeps its seven-argument signature and eight-column result.
While `SourceCrawlClaimPolicy.mode='fenced'`, its body returns zero rows, so an
old worker cannot create an unfenced claim after cutover. The function is not
changed in a database that has not applied the optional attempt addon.

## 3. Operation-binding policy

A candidate operation must satisfy all of:

- `CrawlProposals.state='submitted'`;
- `CrawlProposals.operation_id` is non-null and equals
  `Status.status_sha256`;
- `Status.operation_type='crawl'` and `Status.status='accepted'`;
- `Status.agent_id`, `source_id` agree with the proposal;
- `Status.details` is strict JSON (unknown fields and trailing data rejected)
  whose request, run, principal, agent, owner, source, operation type, parameter
  hash and approval identity match the proposal and approval rows;
- `CrawlApprovals` exists with exact request/run/agent/owner/principal/source,
  proposal hash and approval hash;
- the operation was accepted at or after `approved_at` and before proposal and
  approval expiry;
- the approval was not revoked at or before acceptance;
- `Sources.usr_id` is nonzero and matches a verified `SourceOwnership.user_id`
  equal to the proposal `principal_user_id`;
- the source is live, enabled and not transferred;
- no other active claim already owns the same operation.

Policy:

| Situation | Result | Binding |
| --- | --- | --- |
| No candidate operation | `unattributed` claim | None |
| Exactly one valid candidate | `bound` claim | Exact operation |
| More than one competing candidate | `ambiguous` claim | None |
| One candidate with invalid identity/ownership | `not_attributable` claim | None |
| Candidate already claimed by another active attempt | `conflict` / `already_claimed` | None |
| `already_pending`, `processing`, `completed`, terminal or missing operation | Not a new-claim candidate | None |
| Ordinary legacy crawl | `unattributed` claim | None |

Ambiguous and invalid sources are claimed as **ordinary unattributed work** with
an explicit result code. They are never silently bound and never complete an
operation. `already_pending` is explicitly not ownership of the current attempt.
A source-only completion or `crawl_completed` event never creates a binding.

## 4. Implemented storage

The objects below are part of the unreleased 1.17 fresh-install and migration paths.

### 4.1 `SourceCrawlClaims` — current claim, one row per source

```sql
CREATE TABLE SourceCrawlClaims (
    source_id        BIGINT PRIMARY KEY,
    attempt_id       CHAR(64) NOT NULL UNIQUE,
    claim_request_id CHAR(64) NOT NULL,
    generation      BIGINT NOT NULL CHECK (generation > 0),
    engine_id       TEXT NOT NULL CHECK (length(engine_id) BETWEEN 1 AND 256),
    claimed_at      TIMESTAMPTZ(6) NOT NULL,
    lease_expires_at TIMESTAMPTZ(6) NOT NULL,
    last_updated_at TIMESTAMPTZ(6) NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT uq_source_crawl_claim_generation UNIQUE (source_id, generation),
    CONSTRAINT fk_source_crawl_claim_source
        FOREIGN KEY (source_id) REFERENCES Sources(source_id) ON DELETE CASCADE,
    CONSTRAINT fk_source_crawl_claim_exact_attempt
        FOREIGN KEY (source_id, generation, attempt_id)
        REFERENCES SourceCrawlAttempts(source_id, generation, attempt_id)
        DEFERRABLE INITIALLY DEFERRED,
    CONSTRAINT chk_source_crawl_claim_request CHECK (claim_request_id ~ '^[a-f0-9]{64}$'),
    CONSTRAINT chk_source_crawl_claim_lease
        CHECK (lease_expires_at > claimed_at)
);
```

The deferred FK permits the current row to be upserted before the matching
history insert inside the same transaction. It must resolve by commit.

### 4.2 `SourceCrawlAttempts` — append-only attempts

```sql
CREATE TABLE SourceCrawlAttempts (
    attempt_id       CHAR(64) PRIMARY KEY,
    claim_request_id CHAR(64) NOT NULL,
    source_id        BIGINT NOT NULL,
    generation       BIGINT NOT NULL CHECK (generation > 0),
    engine_id        TEXT NOT NULL CHECK (length(engine_id) BETWEEN 1 AND 256),
    state            TEXT NOT NULL CHECK (state IN (
                         'claimed','superseded','expired','abandoned',
                         'completed','failed','cancelled')),

    claimed_at       TIMESTAMPTZ(6) NOT NULL,
    lease_expires_at TIMESTAMPTZ(6) NOT NULL,
    superseded_by_generation BIGINT,
    terminal_at      TIMESTAMPTZ(6),
    reason_code      VARCHAR(64),

    operation_id     CHAR(64),
    request_id       CHAR(64),
    run_id           TEXT,
    agent_id         TEXT,
    owner            TEXT,
    principal_user_id BIGINT,
    approval_id      CHAR(64),
    approval_sha256  CHAR(64),

    created_at       TIMESTAMPTZ(6) NOT NULL DEFAULT CURRENT_TIMESTAMP,
    last_updated_at  TIMESTAMPTZ(6) NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT uq_source_crawl_attempt_generation UNIQUE (source_id, generation),
    CONSTRAINT uq_source_crawl_attempt_exact_identity
        UNIQUE (source_id, generation, attempt_id),
    CONSTRAINT uq_source_crawl_attempt_request_source UNIQUE (claim_request_id, source_id),
    CONSTRAINT chk_source_crawl_attempt_request CHECK (claim_request_id ~ '^[a-f0-9]{64}$'),
    CONSTRAINT chk_source_crawl_attempt_id CHECK (attempt_id ~ '^[a-f0-9]{64}$'),
    CONSTRAINT chk_source_crawl_attempt_lease CHECK (lease_expires_at > claimed_at),
    CONSTRAINT chk_source_crawl_attempt_binding CHECK (
        (operation_id IS NULL AND request_id IS NULL AND run_id IS NULL AND
         agent_id IS NULL AND owner IS NULL AND principal_user_id IS NULL AND
         approval_id IS NULL AND approval_sha256 IS NULL)
        OR
        (operation_id IS NOT NULL AND request_id IS NOT NULL AND run_id IS NOT NULL AND
         agent_id IS NOT NULL AND owner IS NOT NULL AND principal_user_id > 0 AND
         approval_id IS NOT NULL AND approval_sha256 IS NOT NULL)
    ),
    CONSTRAINT chk_source_crawl_attempt_state CHECK (
        (state = 'claimed' AND superseded_by_generation IS NULL AND terminal_at IS NULL)
        OR (state = 'superseded' AND superseded_by_generation IS NOT NULL AND
            superseded_by_generation > generation AND terminal_at IS NOT NULL)
        OR (state IN ('expired','abandoned','completed','failed','cancelled') AND terminal_at IS NOT NULL)
    ),
    CONSTRAINT chk_source_crawl_attempt_reason CHECK (
        reason_code IS NULL OR reason_code ~ '^[a-z][a-z0-9_]{0,63}$'
    )
);

CREATE INDEX idx_source_crawl_attempts_source
    ON SourceCrawlAttempts (source_id, generation DESC);
CREATE INDEX idx_source_crawl_attempts_request
    ON SourceCrawlAttempts (claim_request_id, source_id);
CREATE INDEX idx_source_crawl_attempts_lease
    ON SourceCrawlAttempts (state, lease_expires_at);
CREATE UNIQUE INDEX uq_source_crawl_attempts_active_operation
    ON SourceCrawlAttempts (operation_id)
    WHERE operation_id IS NOT NULL AND state = 'claimed';
```

The partial unique index allows a later attempt to bind the same operation only
after the prior attempt is no longer `claimed`. The attempt row itself is never
mutated to change its operation identity.

### 4.3 `SourceCrawlClaimPolicy` — controlled cutover

```sql
CREATE TABLE SourceCrawlClaimPolicy (
    policy_id  SMALLINT PRIMARY KEY CHECK (policy_id = 1),
    mode       TEXT NOT NULL CHECK (mode IN ('legacy','fenced')),
    updated_at TIMESTAMPTZ(6) NOT NULL DEFAULT CURRENT_TIMESTAMP
);
INSERT INTO SourceCrawlClaimPolicy(policy_id, mode)
VALUES (1, 'legacy') ON CONFLICT (policy_id) DO NOTHING;
```

Mode is operator-owned and never accepted from an agent, event, model or source.
Re-running the addon must preserve an existing `fenced` mode.

### 4.4 Operator policy authority

`SourceCrawlClaimPolicy` is owned by the deploying administrator. The runtime
claim role receives SELECT only and cannot UPDATE the table. Operators switch
mode with the exclusive-lock function:

```sql
SELECT set_source_crawl_claim_mode('fenced');
SELECT set_source_crawl_claim_mode('legacy');
```

Claim transactions and `update_sources` take the shared advisory lock
`crowler:source-crawl-claim-policy`. A direct administrator UPDATE bypasses that
protocol and is not supported for cutover.

### 4.5 Why not add `Sources` columns

Adding current attempt/generation columns to `Sources` would require changing
every backend's core source shape, grants and query paths, and would not provide
append-only attempt history. The two optional tables keep ordinary source reads
untouched and make the capability additive and reversible.

## 5. Lock order

Claim path:

```text
shared policy advisory lock (or SQLite writer lock)
  -> Sources (selected rows, stable priority/source_id order)
  -> Users (ascending user_id) and administrative grants (when ownership is rechecked)
  -> SourceCrawlClaims / SourceCrawlAttempts (ascending source_id)
  -> read-only CrawlProposals / CrawlApprovals / Status (no proposal row locks)
  -> commit
```

The legacy `update_sources` function takes the same shared advisory lock before
reading the mode. `set_source_crawl_claim_mode` takes the exclusive lock, so an
operator switch waits for in-flight legacy and fenced claims. The runtime role
has SELECT only on the policy table; it cannot execute the operator function or
update the mode directly. Direct database-administrator bypass of the function
is outside the application protocol and must not be used for cutover.

Submission path is proposal → source → approval → users → Status. The claim path
locks source before reading proposals and never waits for a proposal row, so it
cannot form a cycle with submission. Approval issuance/revocation lock source →
users/grants → quota → proposal; the claim path follows source → users/grants
before attempt rows and never locks proposals. Terminal result reporting
(WP-05B3C3) must use source → current claim/attempt → operation and verify the
exact attempt/generation.

## 6. Legacy compatibility and cutover

- `update_sources` signature and returned source columns remain unchanged.
- While the mode is `legacy`, ordinary crawlers continue exactly as today.
- Before calling `set_source_crawl_claim_mode('fenced')`, the operator stops
  legacy claimers and drains or expires all `processing` sources that have no
  attempt row. Those in-flight legacy claims cannot be retroactively fenced;
  they must not be treated as completion evidence.
- In `fenced` mode, `update_sources` returns zero rows. Old workers still run
  safely but receive no new work. New workers use the claim API.
- Rollback is `set_source_crawl_claim_mode('legacy')`; no DDL or data deletion
  is required. Optional tables and history may remain.
- MySQL remains legacy-only. The new API returns unsupported; its procedure is
  unchanged.
- SQLite has no legacy SQL claim function. The new claim helper can be
  implemented for SQLite; ordinary SQLite behavior is unaffected.

## 7. Capability gate

The read-only `CheckSourceCrawlAttemptSchema` verifies the exact composite
history key and reference, the operator mode function, and the runtime's
minimum privileges:

- active schema `1.17` and writer generation `verified-ownership-v1.17`;
- exact tables, columns, primary/unique/foreign keys, checks and indexes;
- the `(source_id, generation, attempt_id)` unique history key and current-claim
  composite reference;
- the `set_source_crawl_claim_mode` operator function;
- `SourceCrawlClaimPolicy` row;
- `SchemaCapabilities` marker `source-crawl-attempt-v1` with a canonical
  checksum;
- runtime privileges: SELECT/INSERT/UPDATE on attempt tables, SELECT on the
  policy table, and no runtime UPDATE privilege on policy;
- SQLite foreign-key enforcement and integrity.

It is not wired into global startup. Ordinary startup and MySQL startup do not
require the optional objects. The claim API calls it before mutation and fails
closed with typed `unsupported`/`unavailable` results.

## 8. Failure and result model

```text
claimed              new current attempt and generation
already_claimed      source is currently owned by an active claim
unattributed         source claimed with no operation binding
ambiguous            competing candidates; claimed unattributed, not bound
not_attributable     one candidate but invalid/transferred/unverified; unbound
conflict             identity or active-operation binding conflict
stale_fence          caller's attempt ID/generation is not current
legacy_mode          fenced claim API not enabled
unsupported          backend/storage capability absent (MySQL/old DB)
unavailable          read/transaction/storage failure; no successful claim
```

Commit uncertainty is reconciled by re-reading the current claim for the exact
source and attempt ID/generation. A matching committed claim is success; a
different current claim is `conflict`/`already_claimed`; absence is `unavailable`
or a safe retry, never a blind second claim. A retry of the same
`(claim_request_id, source_id)` returns the stored attempt and never allocates a
new generation.

## 9. Lifecycle, retention and privacy

- Current claim: one row per source, replaced by a new generation.
- History: append-only. `superseded`, `expired`, `abandoned`, `completed`,
  `failed` and `cancelled` are terminal. WP-05B3C2 writes only `claimed` and
  `superseded` (Stage B claim foundation); later packages write terminal states.
- No prompts, cookies, tokens, secrets, HTML, model text, response bodies or
  unbounded error text. Only IDs, generations, bounded engine/owner/agent names,
  timestamps and stable reason codes.
- No FK from history to `Sources`: deleting a source cascades its current claim
  but historical attempts are retained for audit. Final retention/pruning is a
  separate maintainer decision.
- Owner transfer after a claim does not rewrite the immutable attempt binding;
  new claims revalidate current ownership.

## 10. Migration, rollout and rollback

- The objects are part of the unreleased 1.17 PostgreSQL and SQLite fresh installs
  and the v1.16 -> 1.17 migration scripts.
- Add repeatable same-version development addons with fail-closed structural
  guards. Do not reset an existing fenced mode.
- Update `db_migrations/README.md`; keep `RequiredSchemaVersion='1.17'` and
  `WriterGeneration='verified-ownership-v1.17'`.
- No automatic migration at startup. No persistent/shared database migration in
  this task.
- Rollout: back up, apply addon in a maintenance window, keep `legacy` mode,
  deploy the claim-capable worker, drain legacy processing, then set `fenced`.
- Rollback: call `set_source_crawl_claim_mode('legacy')` (old claim path
  resumes); leave optional tables/history intact; disable the capability marker
  only if a later reviewed procedure requires it. Never drop attempt history as
  a routine rollback.

## 11. Attribution, generation and replay rules

- All submitted proposals with an operation ID are counted before validation.
  A second malformed or missing-approval proposal makes attribution ambiguous;
  it never allows the remaining valid proposal to bind.
- A single proposal is bound only after matching the deterministic
  `CrawlOperationKey`, the authoritative `Status` identity, strict
  `Status.details`, the approval identity and the acceptance chronology.
- Strict details decoding rejects unknown fields, duplicate JSON keys, trailing
  data and oversized payloads. Timestamp comparison allows only database
  microsecond rounding.
- A missing current claim uses `MAX(generation)` from retained history. A
  current claim must match the latest history row exactly. Invalid or
  exhausted generation state fails closed.
- Replay verifies the engine and lease duration from persisted attempt data.
  Limit, priority and interval fields are not persisted, so an exact full
  request-hash replay check would require a schema extension and remains a
  documented limitation.

## 12. Tests

The pure contract tests prove:

- 64-hex unguessable attempt IDs and short-randomness rejection;
- valid unattributed, bound and terminal attempt shapes;
- rejection of malformed IDs, zero source/generation, empty engine, unknown
  state, non-UTC/sub-microsecond timestamps and invalid leases;
- rejection of partial operation bindings, malformed hashes, missing
  run/agent/owner and zero principal;
- exact-fence ownership and stale/not-owner rejection;
- rejection of raw-looking payload/secret fields in the contract.

They are structural only; the persistence tests below prove the SQL behavior.

The implemented Stage B tests prove:

- ordinary `update_sources` returns the same eight columns and selection
  behavior in legacy mode;
- fenced mode returns no rows to the legacy function;
- a new claim increments generation and supersedes the previous attempt;
- concurrent PostgreSQL claimers cannot both own one generation;
- exact attempt-ID/generation fence checks reject stale and wrong-owner calls;
- ambiguous, `already_pending`, invalid ownership and multiple operations never
  bind;
- disabled sources are not selected, and transferred sources are not
  attributable;
- transaction rollback leaves no partial source/attempt/binding;
- idempotent retries return the stored attempt and do not allocate a generation;
- a bound operation can be rebound only after the prior attempt is superseded;
- fresh install, v1.16 -> v1.17 migration and repeatable addon paths converge
  and preserve rows; marker/version/writer values stay
  `1.17`/`verified-ownership-v1.17`;
- missing optional storage fails closed for the opt-in API while ordinary
  SQLite startup still succeeds and MySQL remains unsupported;
- exact `(source_id, generation, attempt_id)` history references reject mixed
  attempt/generation rows on PostgreSQL and SQLite;
- independent PostgreSQL claimers take shared policy locks concurrently while an
  operator mode switch waits with a bounded lock timeout;
- malformed or missing-approval competing operations block binding;
- deterministic operation keys, approval identity, strict details and
  acceptance chronology are verified;
- generation recovery uses retained history and rejects overflow;
- replay rejects changed engine and lease values;
- a genuine scheduler-generated operation binds on PostgreSQL and SQLite.
